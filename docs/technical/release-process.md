# Release process

## Conventions

- **Versions:** [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html).
  Before 1.0.0, a breaking change or a feature bumps the minor version
  (`bump-minor-pre-major`), and a fix bumps the patch. The first release
  after the 0.1.0 baseline is 0.2.0 (`bootstrap-sha` marks where its
  changelog starts).
- **Commits:** [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/).
  The subject is `type(scope)!: summary`:

| Type | Use | In the changelog |
|---|---|---|
| `feat` | a new capability | Features |
| `fix` | a bug fix | Bug Fixes |
| `perf` | a performance change | Performance |
| `refactor` | a code change without a behaviour change | Code Refactoring |
| `docs` | documentation | Documentation |
| `build` | build system, dependencies | Build System |
| `revert` | reverts a commit | Reverts |
| `test`, `ci`, `style`, `chore` | tests, CI, formatting, maintenance | hidden |

Scopes are crate or area names: `model`, `store`, `engine`, `backends`,
`decode`, `dsp`, `analysis`, `app`, `ui`, `ci`, `docs`, and `deps` for dependency updates. A breaking change adds `!`
after the type or scope, or a `BREAKING CHANGE:` footer.

Enable the local hook once per clone:

```sh
git config core.hooksPath .githooks
```

CI checks the PR title (`amannn/action-semantic-pull-request`) and every
commit subject (`scripts/check-commits.sh`). Reword git's default
`Revert "…"` subject to `revert: …`. The local hook lets `fixup!` and
`squash!` commits through so they can be autosquashed, but CI rejects them,
so squash before pushing.

## Repository setup (once)

- **Settings → Actions → General:** enable *Allow GitHub Actions to create
  and approve pull requests*, or release-please cannot open its PR.
- Optionally add a secret **`RELEASE_PLEASE_TOKEN`** (a fine-grained PAT or a
  GitHub App token with *contents* and *pull requests* write access). PRs
  opened with the default `GITHUB_TOKEN` do not trigger other workflows, so
  without it CI does not run on the release PR. In that case, close and
  reopen the PR, or push an empty commit to it, to run CI.
- CI also runs `scripts/check-release-bump.sh` on every push: it applies
  release-please's own updater to a scratch copy and checks that `Cargo.lock`
  stays consistent for `--locked` builds.

## Dependency updates

Dependabot (`.github/dependabot.yml`) opens weekly pull requests for the Cargo
dependencies and for the GitHub Actions. Their titles are `build(deps): bump …`
and `ci(deps): bump …`, which the commit checks and release-please accept.

- The egui crates (`egui*`, `eframe`, `epaint`, `emath`, `ecolor`) update
  together in one pull request, whatever the update type: they must move in
  step.
- Patch updates of every other crate arrive in one pull request.
- Every minor and major update of every other crate has its own pull request,
  because before 1.0 a minor release may break the API.
- The GitHub Actions update in one pull request.

Like any pull request they merge once CI is green on every OS. `opus-decoder`,
`symphonia`, `symphonia-*` (the wildcard includes `symphonia-format-mkv`) are
ignored: they are replaced by the patched copies in `vendor/`
(`[patch.crates-io]`), so they are updated by hand together with the copy.
Ignored crates get no Dependabot security pull requests either; `cargo deny
check` in CI still reports their advisories.

`egui-phosphor` is patched too (`vendor/egui-phosphor`, only its egui
requirement raised) but not ignored: the egui group's pull request that brings
a release targeting the same egui version replaces the copy, and then the copy
and its `[patch.crates-io]` entry are deleted.

## How a release happens

1. Commits land on `master`.
2. The `release-please` workflow keeps a **release PR** open, titled
   `chore: release X.Y.Z`. It bumps:
   - `workspace.package.version` in `Cargo.toml`;
   - the version of every workspace crate in `Cargo.lock` (so `--locked`
     builds keep working);
   - `.release-please-manifest.json`;
   - `CHANGELOG.md`, generated from the commits.
3. Merging the release PR tags `vX.Y.Z` and publishes a GitHub release with
   those notes.
4. In the same workflow run, `release-build.yml` builds and uploads one
   archive per target, each with a `.sha256`:

| Target | Runner | Archive |
|---|---|---|
| `x86_64-unknown-linux-gnu` | ubuntu-22.04 (glibc 2.35) | `.tar.gz` |
| `aarch64-unknown-linux-gnu` | ubuntu-22.04-arm | `.tar.gz` |
| `x86_64-pc-windows-msvc` | windows-latest | `.zip` |
| `x86_64-apple-darwin` | macos-latest (cross-compiled) | `.tar.gz` |
| `aarch64-apple-darwin` | macos-latest | `.tar.gz` |

Each archive holds `fauste-player[.exe]`, `README.md`, `CHANGELOG.md`,
`licenses/Inter-OFL.txt`, `licenses/Phosphor-MIT.txt` and
`licenses/THIRD-PARTY.html` (generated by
`cargo-about` from `about.toml` and `about.hbs`).

Releases created with `GITHUB_TOKEN` do not trigger other workflows, so the
build runs as a job of the release-please workflow, not on a
`release: published` event.

## The website

`pages.yml` builds the website, the landing page in `site/` plus the user
guide (`docs/user`, an mdBook, and its translations in `docs/i18n`), and
deploys it to GitHub Pages at <https://sanchezfauste.com/fauste-player/>,
the guide under `/guide/` and each translation under `/guide/<lang>/`. Its
download links are filled from the latest release by
`scripts/site/build.sh`, so the site is rebuilt on every release: the
release-please workflow calls `pages.yml` in a `site` job after
`binaries`. It also runs when `master` changes the guide, the site or the
scripts, and by hand. Pull requests touching those paths build the site and
run `scripts/site/check-links.sh` and `scripts/site/check-translations.sh`
without deploying.

### The screenshots

`docs/images` holds the English screenshots; they are the default and what
a plain local build shows. On every publish `pages.yml` runs
`scripts/site/localized-screenshots.sh`, which calls
`scripts/site/screenshots.sh --lang <locale> --out <dir>` for English and
each translation, mapping a guide language to the interface locale of
`crates/fp-app/locales` that starts with its code (`es` to `es-ES`, `pt` to
`pt-PT`; a language with no locale keeps the English images). The images are
never committed. `build.sh` receives them through `FAUSTE_SHOTS_DIR`
(`<lang>/main-screen.png`, `<lang>/guide/*.png`): the English ones replace
`images/` in the site, the others go to `images/<lang>/`, and
`guide.py images` points each translated page at its own copy, or leaves the
English link when that screenshot is missing. Pull requests take only the
Spanish set, as a smoke test of the pipeline; the workflow caches the Rust
build, which is done once for all languages.

`docs/images` itself is kept up to date by `.github/workflows/screenshots.yml`.
On a push to `master` that touches `crates/fp-app/src/ui`, the locales,
`crates/fp-app/examples/demo_session.rs` or the screenshot scripts (and on
`workflow_dispatch`), it runs `scripts/site/screenshots.sh --out`, then
`scripts/site/compare-screenshots.sh --apply --prune`, which compares each
PNG with ImageMagick (`compare -metric AE -fuzz 5%`, tolerating 50 pixels:
both are options) so that font antialiasing noise is ignored, and copies
only the images that changed. Regions that change on every run (the
top-bar clock, remaining and elapsed times, meters, the playhead and the
playing cart's sweep) are painted black on both images first, from the
rectangles in `scripts/site/screenshot-masks.txt` (`<image> x,y,w,h`;
update it after a layout change, checking that two runs of
`screenshots.sh --out` compare equal). `--prune` removes only
`main-screen.png` and `guide/*.png`, never other images. If any did, the workflow force-pushes the
branch `docs/retake-screenshots` and opens or updates one pull request,
"docs: retake screenshots", listing them; when nothing differs any more it
closes that pull request with a comment. The work is split in two jobs: `shots` (read-only, no
stored credentials) builds, takes and compares the screenshots and uploads
them as an artifact; `publish` (`contents: write`, `pull-requests: write`,
no build) downloads it and does the commit, the push and the PR. Two runs
never overlap (concurrency group `screenshots`). With the default
`GITHUB_TOKEN`, the repository setting Settings, Actions, General, "Allow
GitHub Actions to create and approve pull requests" must be on, and pull
requests it opens trigger no workflows, so CI does not start by itself:
close and reopen the PR. Alternatively add a repository secret
`SCREENSHOTS_TOKEN` (a fine-grained token with contents and pull requests
write access), which the workflow uses when present and which needs
neither the setting nor the reopening. Look at the images before merging. `docs/i18n` is never
touched. Locally: `scripts/site/screenshots.sh --out /tmp/new` and
`scripts/site/compare-screenshots.sh /tmp/new` list the differences;
`--apply` copies them into `docs/images`.

### The guide in other languages

The English guide in `docs/user` is the only source: pull requests change
English only. The translations are generated with AI and regenerated before
each release, never edited by hand in between. The one mechanical exception:
a pull request that moves, renames or deletes an image in `docs/images` also
updates the image links in `docs/i18n`, so the translated guides keep
building.

- **Languages:** the folders of `docs/i18n`: `es`, `ca`, `de`, `eu`, `fr`,
  `gl`, `it`, `nl`, `pl` and `pt` (European Portuguese), the languages of
  the interface. `docs/i18n/<lang>/` mirrors `docs/user`: the same file
  names, the same `SUMMARY.md` entries (targets, order and nesting), the
  English heading ids (`{#id}` after each translated heading), and
  image links one level deeper (`../../images/…`); the committed images are
  English, and the published site replaces them (see "The screenshots").
- **Metadata:** `docs/i18n/<lang>/translation.toml` holds the language tag,
  its name in the language menu, the book title, the menu label,
  `source-commit` (the full hash of the `master` commit whose `docs/user`
  was translated) and `source-version` (its `git describe --tags`), and the
  notice text (`{version}` and `{commit}` placeholders) with the label of
  the link to the English page.
- **The notice:** every translated page says, in its language, that it was
  translated with AI from the English guide, may contain errors, names the
  version and commit, and links to the same page in English.
  `docs/book-assets/language-menu.js` adds it at the top of each page; the
  start page (`README.md`) also has it in its source, as
  `<div class="ai-notice" role="note">…</div>` linking to `../index.html`,
  so it shows without JavaScript. That link targets the built site (the
  English start page next to the translation's folder); on GitHub's file view
  it is dead.
- **The language menu:** the same script adds a globe button to the top bar
  of every book, English included. It links to the same page in each
  language, or to that language's start page when the page does not exist
  there yet (an English page added after the last regeneration).
- **The browser's language:** the first time someone opens an English page,
  the same script reads `navigator.languages`; the first tag that is
  English (stay) or has a translation (`pt-BR` and `pt-PT` match `pt`)
  decides, and the visitor goes to the same page in that language (the start
  page when it has no such page). Choosing a language in the menu, or the
  notice's link to English, stores the choice in `localStorage`
  (`fauste-player-guide-language`) and the jump never overrides it; links to
  English also carry `?lang=en`, which stores English and stops the jump
  where storage is blocked. Nothing moves without JavaScript, so crawlers
  see the English page.
- **The build:** `scripts/site/build.sh` calls `scripts/site/guide.py build`,
  which copies `docs/` to a staging folder, writes
  `book-assets/languages.js` (the languages, each one's pages, the notice)
  for each book, and runs mdBook with `src`, `language` and `title`
  overridden (`MDBOOK_BOOK__…` variables). `docs/book-assets/languages.js` in
  the source tree is an English-only stub, so a plain `mdbook build docs`
  or `mdbook serve docs` works (without the menu); the script overwrites it
  in the staging copy. The edit link of a translated
  page points at `docs/i18n/<lang>/`.
- **The check:** `scripts/site/check-translations.sh [<site>]` fails when a
  translation's files or `SUMMARY.md` entries differ from `docs/user` at its
  `source-commit` (not at `HEAD`, so English-only pull requests stay
  green), when the metadata is incomplete or `source-commit` is not an
  ancestor of `HEAD`, when the start page lacks the notice with the right
  version and commit, or, given a built site, when a translated page is not
  marked with its language or lacks the menu and notice script. It needs the
  git history (`pages.yml` checks out with `fetch-depth: 0`).

### Regenerating the translations before a release

Do it on a `docs/…` branch from an up-to-date `master`, before merging the
release PR, so the release ships a current guide in every language.

1. List what changed since each translation:
   `python3 scripts/site/guide.py changed [<lang>…]` prints the English pages
   added, modified or deleted since its `source-commit`
   (`git diff --name-status <source-commit> HEAD -- docs/user`).
2. For each language, translate the changed pages with AI from `docs/user`
   at the branch's base commit (`git merge-base HEAD origin/master`):
   - keep code, keys, file paths, commands and links unchanged; image links
     become `../../images/…`;
   - use, for every interface label, the exact text of the app's locale file
     (`crates/fp-app/locales/<locale>/main.ftl`), so the guide matches the
     screen;
   - translate headings, and give every heading below the title the id of
     its English heading (`## Ajustes {#settings}`), so links to anchors stay
     unchanged and the language menu keeps the anchor;
   - copy new pages and `SUMMARY.md` entries, delete removed ones.
3. Set `source-commit` to that base commit (a `master` commit, so rebasing
   the branch does not invalidate it) and `source-version` to
   `git describe --tags <source-commit>`, and update the version and commit
   in the notice of `README.md`.
4. Build and check:
   `scripts/site/build.sh target/site && scripts/site/check-links.sh target/site && scripts/site/check-translations.sh target/site`.
5. Commit as `docs(user): regenerate the <language> guide` (one commit per
   language or one for all) and open the pull request.

To add a language, create `docs/i18n/<lang>/` with a `translation.toml`
(copy one and translate its strings) and a full translation made as in
step 2, then add the language to the list above.

One-time step for the maintainer: **Settings → Pages → Source: GitHub
Actions**.

## Rebuilding the assets of a release

Run **Actions → release-build → Run workflow** with the tag (for example
`v0.2.0`). The assets are uploaded again with `--clobber`. The website's
download links do not change by themselves: run **Actions → pages → Run
workflow** afterwards if the asset names changed.

## Building an archive locally

```sh
cargo install cargo-about --locked --features cli   # optional outside CI
scripts/package-release.sh x86_64-unknown-linux-gnu  # → dist/fauste-player-<v>-<target>.tar.gz
```

The Windows release build is a GUI program (`windows_subsystem = "windows"`
in `main.rs`, active only for `windows` without `debug_assertions`), so it
opens no console window. `scripts/package/windows.sh` runs
`scripts/check-windows-gui.sh` on `fauste-player.exe` and fails the job when
the PE Subsystem field is not 2 (GUI); CI runs that script's `--self-test`
(a synthetic header) on Linux and Windows. Debug builds keep their console, so
`cargo run` still prints logs and `--version`. In a release build,
`--version`, `--help` and start-up errors appear in a message box
(`cli::emit`).

## Before merging a release PR

- CI is green on all three OSes, and `cargo deny check` passes.
- The changelog reads well; edit the release PR if needed.
- A manual smoke test on at least one OS: the four players play, a segue
  overlaps, CUE works, and a restart restores paused positions.

## Packaging (Phase 5)

`release-build.yml` attaches these packages to every release, each with a
`.sha256`:

| Job | Produces | Script |
|---|---|---|
| `build` (Linux matrix entries, ubuntu-22.04 and 22.04-arm) | archive, `.deb` (cargo-deb), `.rpm` (cargo-generate-rpm), AppImage (appimagetool) | `scripts/package-release.sh`, `scripts/package/linux.sh` |
| `build` (Windows) | archive, `.msi` (cargo-wix, WiX Toolset v3) | `scripts/package/windows.sh` |
| `build` (macOS entries) | archives per architecture; each also keeps its binary as a one-day artefact | `scripts/package-release.sh` |
| `macos-dmg` | universal `.app` (lipo of the two `build` binaries, `PREBUILT_DIR`) in a `.dmg`; it compiles an architecture only when its build failed | `scripts/package/macos.sh` |
| `flatpak-sources`, `flatpak`, `flatpak-release` | `cargo-sources.json` (flatpak-cargo-generator), then the bundle built offline with flatpak-builder | `packaging/flatpak/com.sanchezfauste.FaustePlayer.yml` |
| `stores` (separate workflow, `stores.yml`) | the Microsoft Store MSIX, the snaps, the Flathub update, WinGet and the AUR (see "Stores") | `scripts/package/msix.sh`, `snap/snapcraft.yaml`, `scripts/package/flathub-manifest.py`, `scripts/package/aur.sh` |
| `unsigned-note` | a section in the release notes listing the installers built without their signing secrets, with a link to the user guide's instructions (added once) | `release-build.yml` |

**Shared metadata** lives in `packaging/`, with one application id,
`com.sanchezfauste.FaustePlayer`:
- the icons (SVG, PNG sizes, `.ico`). `fauste-player.svg` is the source: after
  changing it, run `scripts/package/icons.sh` (inkscape and ImageMagick) and
  commit the regenerated PNGs and `.ico`. The window icon, the packages, the
  `.icns` and the website favicon all read these files;
- the desktop entry;
- the AppStream metainfo. It carries no version: `scripts/package/metainfo.sh`
  adds the one being packaged;
- `Info.plist` and the WiX source.

**Build rules:**
- Every Linux package ships the archive's binary (built with `jack`; see
  [backends](backends.md)), so the packages and the archive never differ.
- The deb's dependencies are read from the binary. The build therefore runs on
  the oldest supported image, ubuntu-22.04, and CI's `release-baseline` job
  builds all three Linux packages on every push.
- Tools fetched while packaging are pinned and checked before they run:
  appimagetool is release 1.9.1 (SHA-256 per architecture in
  `scripts/package/linux.sh`), flatpak-cargo-generator a fixed commit of
  flatpak-builder-tools (SHA-256 in `scripts/package/flatpak-cargo-sources.sh`),
  cargo-about for the builds outside `package-release.sh` release 0.9.2
  (SHA-256 per architecture in `scripts/package/notices.sh`), and the snap's
  rustup-init release 1.29.2 (SHA-256 per architecture in
  `snap/snapcraft.yaml`). Bump each together with its checksums.

**Local builds:**
- Linux: `scripts/package/linux.sh x86_64-unknown-linux-gnu [version] [deb,rpm,appimage]`.
- Windows: `scripts/package/windows.sh x86_64-pc-windows-msvc`, in Git Bash
  with cargo-wix and WiX v3.
- macOS: `scripts/package/macos.sh`.

**Dry run:** a pull request that touches `packaging/`, `scripts/package*`
or `release-build.yml` runs `release-build` as a dry run: it builds every
package, including the MSI, the dmg and the Flatpak, and uploads nothing.
The same run can be started by hand with `dry_run` checked and any ref as
`tag`.

**Superseded runs:** a new push to a pull request cancels the CI run,
the commit check and the dry run it replaces. Runs on `master` and release
builds are never cancelled. Editing only the PR description runs no check,
and editing the title re-checks only the title.

### Signing (optional secrets)

| Secret | Used for |
|---|---|
| `WINDOWS_CERT_PFX` (base64 of a `.pfx`), `WINDOWS_CERT_PASSWORD` | signtool signs `fauste-player.exe` inside the MSI and the MSI itself, with an RFC 3161 timestamp |
| `APPLE_CERT_P12` (base64 of a *Developer ID Application* `.p12`), `APPLE_CERT_PASSWORD` | codesign with the hardened runtime, for the app and the dmg (without it the app gets an ad-hoc signature, so Gatekeeper offers *Open Anyway* instead of reporting it damaged) |
| `APPLE_ID`, `APPLE_TEAM_ID`, `APPLE_APP_PASSWORD` (app-specific password) | notarytool notarisation, then stapling the ticket to the dmg |

- **Without these secrets** the packages are built unsigned. The getting
  started guide explains the SmartScreen and Gatekeeper prompts users then
  see.
- **Portable archives** are never signed.
- **Passing the secrets:** release-please passes them to `release-build`
  with `secrets: inherit`.

## Stores

`stores.yml` publishes every release to the app stores and package
repositories. release-please calls it in a `stores` job after `binaries`,
because WinGet and the AUR read the release's assets (the MSI, the Linux
archives). It can be run by hand (**Actions → stores → Run workflow**) with
an existing release tag, with `dry_run` to build and check without
publishing. Every job builds from the tag, so the tag must carry the store
packaging: the workflow refuses other tags, and tags made before it
(v0.10.0 and earlier).

| Job | Store | What it does | Publishes when |
|---|---|---|---|
| `msstore` | Microsoft Store | builds an unsigned MSIX (`scripts/package/msix.sh`; the Store signs it) and submits it with the Microsoft Store CLI (`msstore publish`) | the `MSSTORE_*` secrets and variables are set |
| `snap` | Snap Store | builds `snap/snapcraft.yaml` on amd64 and arm64 (`snapcore/action-build`) and uploads and releases it (`snapcore/action-publish`) | `SNAPCRAFT_STORE_CREDENTIALS` is set |
| `flathub` | Flathub | writes the Flathub manifest (`scripts/package/flathub-manifest.py`: the in-tree manifest with the release's git tag and commit as its source) and `cargo-sources.json`, lints both with `flatpak-builder-lint`, and opens a pull request on `flathub/com.sanchezfauste.FaustePlayer` | `FLATHUB_TOKEN` is set |
| `winget` | WinGet | opens a pull request on `microsoft/winget-pkgs` with the release's MSI (`vedantmgoyal9/winget-releaser`) | `WINGET_TOKEN` is set |
| `aur` | AUR | writes the `fauste-player-bin` PKGBUILD from `packaging/aur/PKGBUILD.in` (`scripts/package/aur.sh`, with the checksums of the release archives), checks it with `makepkg --printsrcinfo` and `namcap`, and pushes it | `AUR_SSH_PRIVATE_KEY` is set |

- **Pre-releases** (a version with `-`) go only to the Snap Store's `beta`
  channel; the other stores skip them.
- **Dry run:** a pull request that touches `snap/`, `packaging/`, the store
  scripts or `stores.yml` builds the MSIX and both snaps, lints the Flathub
  manifest and checks the PKGBUILD, and publishes nothing.
- **Shared metadata:** the snap, the Flathub build and the stores' listings
  read the AppStream metainfo (`packaging/linux/com.sanchezfauste.FaustePlayer.metainfo.xml`),
  whose screenshots point at `docs/images` on `master`. The MSIX logos in
  `packaging/windows/msix/Assets` are rendered by `scripts/package/icons.sh`.
- **Toolchain:** the snap's `rust-deps` part installs the version
  `rust-toolchain.toml` pins, with rustup. The Flatpak and Flathub builds use
  the SDK's `rust-stable`.
- **Notices:** the snap, the Flatpak and Flathub ship `THIRD-PARTY.html`
  from `scripts/package/notices.sh` (cargo-about) where the About window
  looks for it. The Flatpak and Flathub builds are offline, so CI writes it
  next to `cargo-sources.json` and the manifest lists it as a file source.
- **Builds without a store:** on a release the MSIX, the snaps, the Flathub
  manifest and the PKGBUILD are built and checked even for stores not set up
  yet, so a packaging break shows on the release run before it matters.

### Secrets and variables

Set under **Settings → Secrets and variables → Actions**. Secrets hold
credentials; variables hold public identifiers.

| Name | Kind | Value |
|---|---|---|
| `MSSTORE_TENANT_ID`, `MSSTORE_CLIENT_ID`, `MSSTORE_CLIENT_SECRET` | secrets | the Microsoft Entra application linked to Partner Center (see below) |
| `MSSTORE_SELLER_ID` | secret | Partner Center → Account settings → Legal info → Seller ID |
| `MSSTORE_PRODUCT_ID` | variable | the Store ID of the app (`9N…`), Partner Center → Product identity |
| `MSSTORE_IDENTITY_NAME`, `MSSTORE_PUBLISHER`, `MSSTORE_PUBLISHER_DISPLAY_NAME` | variables | Package/Identity/Name, Package/Identity/Publisher (`CN=…`) and Package/Properties/PublisherDisplayName from Product identity |
| `SNAPCRAFT_STORE_CREDENTIALS` | secret | the output of `snapcraft export-login --snaps=fauste-player --acls=package_access,package_push,package_update,package_release -` |
| `SNAP_CHANNEL` | variable (optional) | the channel releases go to; default `stable` |
| `FLATHUB_TOKEN` | secret | a token of a maintainer of `flathub/com.sanchezfauste.FaustePlayer` that can push branches and open pull requests there: fine-grained (*contents* and *pull requests* write) if the flathub organisation accepts fine-grained tokens, otherwise classic with `public_repo` |
| `WINGET_TOKEN` | secret | a classic token with the `public_repo` scope, of the account that owns the fork of `microsoft/winget-pkgs`; best a separate bot account (`WINGET_FORK_USER`), since `public_repo` on the maintainer's account can also push to this repository |
| `WINGET_IDENTIFIER`, `WINGET_FORK_USER` | variables (optional) | the package identifier (default `SanchezFauste.FaustePlayer`) and the fork's owner (default the repository owner) |
| `AUR_SSH_PRIVATE_KEY` | secret | a private SSH key whose public key is in the AUR account |
| `AUR_USERNAME`, `AUR_EMAIL` | variables (optional) | the author of the AUR commits |

### One-time setup per store

**Microsoft Store**
1. Register as an individual developer in
   [Partner Center](https://partner.microsoft.com/dashboard) (free for
   individuals) and create a new app, reserving the name *Fauste Player*.
2. Copy the Product identity values into the `MSSTORE_*` variables.
3. Under Account settings → User management → Microsoft Entra applications,
   create (or add) an application with the *Manager* role and a key; its
   tenant ID, client ID and key go into the `MSSTORE_*` secrets.
4. Make the first submission by hand: once the variables are set, run the
   workflow with `dry_run` for the latest release (one that carries the
   store packaging), download the `msix` artefact, and upload it in Partner
   Center together
   with the listing (description, screenshots, privacy policy URL, age
   rating). The `runFullTrust` capability needs a short justification (a
   desktop program that opens audio devices and music files).
5. Once it is certified, later releases are submitted by the workflow; each
   still goes through certification. The workflow's `msstore publish`
   replaces any pending draft with a new submission made from the last
   published one, so listing edits are made in Partner Center after a
   release's submission, not left in a draft before it.

**Snap Store**
1. Create an account on [snapcraft.io](https://snapcraft.io) and register
   the name: `snapcraft register fauste-player`.
2. Export the credentials (see the table) into `SNAPCRAFT_STORE_CREDENTIALS`.
3. The first release passes an automatic review. Ask in the Snapcraft forum
   (store-requests) for the `alsa` interface to be connected automatically;
   until then users run `snap connect fauste-player:alsa` for direct ALSA
   (bit-perfect) devices and MIDI. PulseAudio and PipeWire output work
   without it (`audio-playback`).

**Flathub**
1. The application ID must belong to a domain or code host the developer
   controls: `com.sanchezfauste.FaustePlayer` is under `sanchezfauste.com`,
   where Flathub's verification later asks for a token at
   `https://sanchezfauste.com/.well-known/org.flathub.VerifiedApps.txt`. That
   site is the Jekyll repository `sanchezfauste/sanchezfauste.github.io`,
   which publishes a dot-directory only when its `_config.yml` lists it
   (`include: [.well-known]`).
2. Fork [flathub/flathub](https://github.com/flathub/flathub), branch from
   `new-pr`, add the `com.sanchezfauste.FaustePlayer.yml` and `cargo-sources.json`
   (and `THIRD-PARTY.html`) of the `flathub` artefact of the latest
   release's stores run, and open a
   pull request against `new-pr`. Reviewers ask about the permissions:
   `--device=all` (ALSA hw: devices and MIDI), `--filesystem=home:ro`
   (music libraries read in place), `--share=network` (the remote API).
3. After the merge Flathub creates `flathub/com.sanchezfauste.FaustePlayer` and
   gives the submitter write access. Create `FLATHUB_TOKEN` for it; from
   then on every release opens an update pull request there, which
   Flathub's CI builds and which is merged by hand.
4. Verify the app in the Flathub developer portal.

**WinGet**
1. Fork [microsoft/winget-pkgs](https://github.com/microsoft/winget-pkgs)
   under the repository owner's account.
2. Submit the first version by hand:
   `wingetcreate new <MSI URL of the latest release>` (identifier
   `SanchezFauste.FaustePlayer`). The action only updates packages that
   already exist.
3. Create `WINGET_TOKEN`.

**AUR**
1. Create an [AUR](https://aur.archlinux.org) account and add an SSH public
   key to it; the private key goes into `AUR_SSH_PRIVATE_KEY`.
2. The first push creates `fauste-player-bin`; nothing else is needed.
